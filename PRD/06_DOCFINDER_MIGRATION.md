# 06. DocFinder 이관 보고서

**작성일** 2026-07-22
**대상** `Fable/docfinder` (Electron 판) → `32_exam_pool` 근거 문서 탭 (Python 판)

---

## 요약

**코드 이관은 이미 끝나 있다.** `app/pdf_indexer.py` 첫 줄이 "DocFinder 로직 재구현"이라고 밝히고 있고,
커밋 `eec1e4d`("근거검색 강화 — PDF 미리보기·해시태그·폴더선택")에서 검색·미리보기·폴더선택까지 들어왔다.

따라서 이 문서는 "옮기는 방법"이 아니라 **"옮긴 뒤 무엇이 비어 있고 무엇을 손봐야 하는가"**를 다룬다.

중요한 것은 이관 과정에서 **Electron 판의 핵심 버그 2개가 구조적으로 사라졌다**는 점이다.
같은 실수를 되돌리지 않으려면 왜 사라졌는지를 알아야 한다 (2장).

## 1. 아키텍처 대조

| | DocFinder (Electron) | ExamPool (Python) | 평가 |
|---|---|---|---|
| 텍스트 추출 | pdf.js `getTextContent()` + 자체 조립 휴리스틱 | PyMuPDF `page.get_text()` | **Python 우세** |
| 검색 엔진 | 손으로 짠 JS BM25 (`search.js`) | SQLite FTS5 `bm25()` | **Python 우세** |
| 색인 저장 | `index.json` 전문 통째로, 동기 read/write | SQLite | **Python 우세** |
| 한국어 조사 처리 | 없음 | prefix wildcard `"빛"*` | **Python 우세** |
| 미리보기 | 렌더러에서 pdf.js 캔버스 + textLayer | 서버에서 PNG 렌더 후 `<img>` | **Python 우세** |
| 하이라이트 | textLayer span 단위 정규식 | PyMuPDF `search_for()` 좌표 | **Python 우세** |
| 색인 속도 | 2183p / 약 20초 | 606p / 7.9초 (≈2183p 환산 28초) | 비슷 |
| 검색 속도 | 약 40ms | 약 2ms | **Python 우세** |

**결론: Electron 판을 되살릴 이유가 없다.** 남은 것은 UI 기능 격차와 Python 판 자체의 품질 문제뿐이다.

## 2. Electron 판의 버그와, Python 판이 그것을 피한 이유

> 이 장이 이 보고서에서 가장 중요하다. 앞으로 하이라이트를 손볼 때 반드시 참고할 것.

### 2-1. `--scale-factor` 누락 (Electron 판 전용, 이관으로 소멸)

pdf.js 3.x의 `renderTextLayer`는 글자 span을 `left: calc(var(--scale-factor) * 123.4px)`로 배치한다.
Electron 판은 이 CSS 변수를 어디에도 설정하지 않아 `calc()` 전체가 무효가 되고,
`left`/`top`/`font-size`가 초기값으로 떨어져 **텍스트 레이어가 실제 글자와 어긋난 채 쌓였다.**
앱 로그(`run.err.log:10`)에 pdf.js가 직접 경고를 남기고 있었다.

→ Python 판은 서버에서 PNG를 굽고 좌표를 PDF 좌표계에서 직접 계산하므로 **이 문제 자체가 존재하지 않는다.**

### 2-2. 색인용 텍스트 ≠ 하이라이트용 텍스트 (부분적으로만 소멸 — 주의)

Electron 판은 색인은 `assembleText()`로 **조각을 이어붙인 문자열** 위에서 만들고,
하이라이트는 `app.js`에서 **이어붙이지 않은 개별 span마다** 정규식을 돌렸다.
한글 PDF는 한 단어가 여러 조각으로 쪼개지는 일이 흔해서
(코드 주석도 "징 계 기 준" 문제를 인정하고 있다), 키워드가 두 span에 걸치면
**검색은 100% 일치라고 하는데 하이라이트는 하나도 안 찍히고 스크롤도 안 되는** 상태가 됐다.

→ Python 판은 `page.search_for(t)`가 PDF 텍스트 레이어에서 직접 좌표를 찾으므로 대부분 해결됐다.

**다만 같은 계열의 위험이 옅게 남아 있다.** 검색은 FTS5(`get_text()` 결과 + unicode61 토크나이저 +
prefix wildcard)로 맞히고, 하이라이트는 `search_for()`(글리프 단위 탐색)로 찾는다. **경로가 둘이다.**
줄바꿈으로 단어가 쪼개졌거나 정규화가 어긋나면
**`match_pct`는 100%인데 형광펜은 한 개도 안 그려지는** 페이지가 나올 수 있다.

권고: `render_page_png`에서 `search_for` 결과가 0개면 그 사실을 응답에 실어
UI가 "이 페이지에서 정확한 위치를 찾지 못했습니다"를 표시하게 한다. 조용히 실패하지 않게 하는 것이 핵심이다.

## 3. 남은 기능 격차 (DocFinder에 있었으나 ExamPool에 없는 것)

| # | 기능 | 현재 상태 | 우선순위 |
|---|---|---|---|
| 1 | **색인 진행률 표시** (현재/전체 + 파일명) | `index_folder(progress=)` 콜백이 **이미 구현돼 있는데** `routes_doc.py:27`이 넘기지 않아 도달 불가. UI는 "색인 중…" 정적 텍스트 | **높음** |
| 2 | **제외 문서 목록** (텍스트 없음/열기 실패) | 백엔드가 `skipped[]`에 사유까지 담아 반환하는데, UI는 `alert()`로 **개수만** 보여줌 | **높음** |
| 3 | **키워드별 구분 색상 + 범례** | 전부 단색. 스니펫 `#ffe9a8`, 미리보기 `fill=(1,0.85,0.3)` 고정 | 중 |
| 4 | **첫 일치 위치로 자동 스크롤** | 전체 페이지 `<img>`만 갈아끼움. API가 좌표를 안 돌려줌 | 중 |
| 5 | **입력 즉시 검색 (디바운스)** | 해시태그 칩 방식(Enter로 확정). 의도된 설계일 수 있음 | 낮음 |

1·2번은 **백엔드가 이미 데이터를 만들고 있는데 배선만 안 된 상태**라 비용 대비 효과가 가장 크다.

3·4번은 PRD에 명세된 적이 없다(DocFinder에만 있던 UX). 넣을지 여부는 판단이 필요하다.
5번은 해시태그 칩 UI가 오히려 낫다고 보면 **격차가 아니라 개선**으로 봐야 한다.

## 4. Python 판 자체의 문제 (이관과 무관하게 손봐야 할 것)

### 4-1. `page_fts`가 전문을 중복 저장한다 — **높음**

`pdf_indexer.py:18` 주석은 "document_page를 external-content로 미러링"이라고 하지만,
실제 `CREATE VIRTUAL TABLE`에 `content=` 옵션이 없다. **standalone FTS5**라서
본문이 `document_page.text`와 `page_fts.body`에 **두 번** 저장된다. DB 크기가 2배다.

→ `content='document_page', content_rowid='id'`로 바꾸면 용량이 반으로 줄고 동기화 위험도 사라진다.
스키마 변경이므로 재색인이 필요하다.

### 4-2. 재색인이 문서 수에 비례해 느려진다 — **중**

`DELETE FROM page_fts WHERE document_id = ?` (`pdf_indexer.py:76`)에서 `document_id`는
`UNINDEXED` 컬럼이라 **매 문서마다 FTS 테이블 전체를 훑는다.** 문서가 늘수록 재색인이 제곱으로 느려진다.

### 4-3. 색인이 요청 하나를 통째로 붙잡는다 — **중**

`routes_doc.py:24`가 동기 함수라 FastAPI 스레드풀에서 돌아 이벤트 루프는 안 막히지만,
**요청 자체가 스캔이 끝날 때까지 열려 있다.** 606p에 7.9초이므로 교과서 폴더가 커지면
브라우저 타임아웃 구간에 들어간다. 3번 항목(진행률)과 함께 작업 ID 방식으로 바꾸는 게 자연스럽다.

### 4-4. `/api/pick-folder`가 서버 스레드에서 tkinter 모달을 띄운다 — **중**

`routes_doc.py:29-46`. 사용자가 대화상자를 안 닫으면 스레드풀 워커가 무기한 묶인다.
tkinter를 메인 스레드 밖에서 쓰는 것도 공식 지원 밖이다. 로컬 전용 앱이라 당장은 돌지만 취약하다.

### 4-5. `document.file_path`에 UNIQUE 제약이 없다 — **낮음**

중복 제거를 `SELECT ... WHERE file_path = ?` 조회로만 한다(`pdf_indexer.py:74`).
색인이 두 번 겹쳐 돌면 같은 파일이 두 문서로 들어갈 수 있다.

### 4-6. `match_pct`는 상대값이라는 점을 UI가 말하지 않는다 — **낮음**

`pdf_indexer.py:156`의 `pct = (score / best) * 100`은 **그 검색 안에서 최고점을 100%로 놓은 상대 환산**이다
(DocFinder에서 그대로 물려받은 방식). 형편없는 결과 하나만 잡혀도 100%로 표시된다.
"일치율"이라는 이름이 절대 신뢰도처럼 읽히므로, 라벨을 "상대 순위" 계열로 바꾸거나 툴팁으로 설명하는 게 정직하다.

### 4-7. `render_page_png`가 매 요청마다 PDF를 새로 연다 — **낮음**

`pdf_indexer.py:186,195`. HTTP `Cache-Control: 600s`가 있어 체감 문제는 작지만,
페이지를 ◀▶로 넘길 때마다 `fitz.open()`이 반복된다. LRU 캐시를 얹을 여지가 있다.

> 참고: Electron 판의 최대 병목이던 "결과 클릭 때마다 `fs.readFileSync`로 PDF 전체를 메인 프로세스에서
> 동기 로드 + 캐시 없음 + `doc.destroy()` 미호출로 인한 누수"는 Python 판에 **없다.**
> 사용자가 겪던 버벅임의 주원인이 이것이었으므로, 이관만으로 체감 속도 문제는 대부분 해소된다.

## 5. 테스트 격차

`tests/test_pdf_indexer.py` 98줄이 전부이고, **`routes_doc.py`를 건드리는 테스트가 하나도 없다**
(`tests/`에 FastAPI `TestClient`가 없다).

현재 검증되는 것: `_fts_query` 변환, 해시태그 파싱, AND 검색 적중, `match_pct` 범위, `doc_id` 필터.

**검증되지 않는 것:**
- `collect_pdfs` 재귀 스캔
- `_extract` / `MIN_CHARS` 스캔본 건너뛰기
- `index_folder`의 재색인 교체 경로와 `skipped` 사유
- `render_page_png` — **2-2절의 잠재 버그가 바로 여기 있는데 테스트가 없다**
- 모든 HTTP 라우트

PRD 04(`:85`)가 "실제 PDF 없이 도는 단위 테스트"를 요구하므로,
PyMuPDF로 텍스트 PDF를 메모리에서 생성해 픽스처로 쓰면 위 항목 대부분을 커버할 수 있다.

## 6. PRD 대비 미구현

`PRD/03_PHASES.md:16`이 요구하는 **"근거 검색 → 드래그로 근거 저장 (출처·원문 자동 입력)"**이
아직 없다. 근거 문서 탭에 드래그 소스가 없고, 문항 설계 탭의 근거 검색은 별개의 단순 목록이다.
`PRD/03_PHASES.md:38`의 인수 조건("인덱싱 → 검색 → 드래그 근거 저장 end-to-end")도 미충족이다.

**이것이 기능 격차 목록(3장)보다 우선순위가 높다.** 3장은 DocFinder와의 비교일 뿐이지만,
이쪽은 ExamPool 자체 명세를 못 채운 상태다.

## 8. Electron 판 처리

`Fable/docfinder`는 **기능적으로 완전히 대체되었다.** 유지할 이유가 없다.

- `src/` + `test/` 실코드는 48KB(파일 9개), `node_modules/`가 486MB
- 되살릴 가치가 있는 로직은 없음 — Python 판이 모든 항목에서 동등하거나 낫다 (1장)
- 다만 `assembleText()`의 한글 조각 이어붙이기 휴리스틱은 **실패 사례로서** 기록 가치가 있어 2-2절에 남겨두었다

→ 참고용으로 소스만 보관할지, 폴더째 삭제할지는 별도 결정 사항이다.
